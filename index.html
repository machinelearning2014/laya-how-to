The mental model

You give Laya a state (a string, a dict, or a list of conversation turns) and a dict of typed questions. It routes to a checkpoint and answers every question at once.

The reason it is fast is structural, not an optimization: the state and every question's options are packed into one sequence, with each option occupying its own masked slot. A single forward pass scores all the slots, so eight questions cost about the same as one. That is why predict has no batch dimension to exploit for a single state, and why adding questions is nearly free.

Why this matters for your latency

Adding questions to a request is close to free. Splitting one request into eight separate predict calls is not — that is eight routes and eight forward passes.

Setup and checkpoints

pip install laya                      # Python 3.10+
pip install "laya[structured]"        # adds pydantic, for schema= typed output
pip install "laya[serve]"             # adds the HTTP server
from laya import Router

router = Router()                 # lazy: nothing downloads until the first predict
router = Router(preload=True)        # load all three up front
router = Router(max_loaded=1)         # keep only one checkpoint resident
router = Router(device="cpu")         # pin the device (default: cuda, else mps, else xpu, else cpu)
router = Router(agent_kwargs={"compile": True})   # Agent-level options reach the Router here

Three checkpoints, and the router picks between them per request by detected script and language. Routing itself loads nothing, so it is safe to call on every request.

Route precedence runs: explicit model, then task, then detected workflow, then explicit lang, then lang_guess, then detection, then default.

Constructor is plural

Router(models=...) overrides the checkpoint table. The singular model= is a per-call argument on predict, not a constructor kwarg.

Writing questions

Three types. Each question is a dict with type, instructions, and criteria.

choice

Pick one label. Criteria may be a dict of label to description, or a plain list of labels.

"department": {"type": "choice",
               "instructions": "Which department should handle `message`?",
               "criteria": {"billing": "invoices, payments, refunds",
                            "technical": "bugs, outages, system errors",
                            "other": "everything else"}},

# short form: labels only. None or "" means "no description".
"topic": {"type": "choice", "criteria": ["billing", "technical", "other"]}

score

An ordered scale of any length. You get back the expected level as a float, plus the full distribution.

"urgency": {"type": "score",
            "instructions": "How urgent is `message`?",
            "criteria": ["not urgent", "soon", "blocking"]}   # -> 1.79

noul

A yes/no question under uncertainty. Always returns P(true) in 0..1, whatever you call the two sides.

"churn_risk": {"type": "noul",
               "instructions": "Does `message` threaten to cancel or leave?"}   # -> 0.84

# criteria is optional. If given, it must be keyed exactly true/false.
"refund_requested": {"type": "noul",
                     "instructions": "Does `message` ask for money back?",
                     "criteria": {"true": "asks for a refund or a charge reversed",
                                  "false": "no refund requested"}}

# labels only change the text shown to the model. The number is still P(true).
"labels": {"true": "A", "false": "B"}

The backtick convention

Every preset in the library names the state field it reads inside backticks: "What does the customer want in `message`?". presets.state_field() scrapes that name back out, and the CLI and MCP server use it to know where to put your text. Plain predict with a string state does not need it, but adopting it keeps a question set portable to the CLI and to decide.

Limits worth knowing

  • Each option's rendered text is truncated to 48 tokens. More labels means fewer tokens each.
  • The option head shares head_max_len (default 192). Raise it for many-label questions.
  • Core imposes no cap on question or option counts. The HTTP server does: 64 questions, 100 choice options, 32 score levels, 512 total options.
  • If the masked slots cannot fit inside max_len, you get a ValueError naming the question — and raising head_max_len can make it worse by leaving less room for state.

Reading the result

Four top-level keys: model, answers, usage, routing. The routing key is added by Router; a bare Agent returns the other three.

# choice
{"type": "choice", "choice": "billing",
 "probabilities": {"billing": 0.9875, "technical": 0.0071, "other": 0.0054},
 "confidence": 0.93, "answer_confidence": 0.9875}

# score
{"type": "score", "score": 1.7901,
 "legend": {"0": "not urgent", "1": "soon", "2": "blocking"},
 "probabilities": {"0": 0.0337, "1": 0.1424, "2": 0.8238},
 "confidence": 0.34, "answer_confidence": 0.8238}

# noul
{"type": "noul", "noul": 0.8429,
 "confidence": 0.8429, "answer_confidence": 0.8429}

Every answer also carries "action": {"act_probability": ...} from a separate head. It is always 1.0 in these runs; the examples above omit it for length.

Did the model actually see my whole state?

result["usage"]
# {"input_tokens": 401, "output_tokens": 0, "state_tokens": 21,
#  "state_tokens_dropped": 0, "truncated": False, "truncated_questions": []}

Read usage["truncated"] instead of estimating from string length. Long states are silently trimmed to fit max_len (512 on english, 1024 on multilingual). usage also gains an options entry when the head budget collapsed two options onto the same tokens — a signal that your answer is limited by the budget rather than by the model.

output_tokens is always 0. Laya never generates text.

Confidence and abstention

Two different confidences

Each answer carries both, and they measure different things.

Typeconfidenceanswer_confidence
choicenormalized Shannon entropymax(p), the top option's probability
scorenormalized Shannon entropymax(p), the top level's probability
noulmax(p)max(p) — identical to the above here

Gate on answer_confidence. It is the calibrated quantity — the one temperature scaling fits and ECE measures — and it means the same thing across all three types. The entropy confidence is useful for ranking, but it drifts with how many options a question has, so a threshold on it does not transfer between questions.

Why that distinction bites

Every answer from the tour, sorted by how much the model actually committed to it:

QuestionTypeAnsweranswer_confidenceReads as
departmentchoicebilling0.9875confident
refund_requestednoul0.9060.906confident yes

security_related, no labelsnoul0.3730.627confident no

The fifth row is the trap. security_related answers 0.373, which reads like a low-confidence result, but answer_confidence is 0.627 — the model is confidently saying no. Gating on the raw noul value would abstain on its most decisive answer. sentiment at 0.46 is the one actually worth escalating: it sits between "annoyed" and "angry", and the model is telling you so.

The sixth row is a different lesson. Adding custom labels to that same question moves it from 0.373 to 0.5386 — labels change the text the model reads, so they change the answer, not just the display.

Opt-in abstention

result = router.predict(state, questions, min_confidence=0.9)
department {'choice': 'billing', 'answer_confidence': 0.9875, 'abstention': 'passed'}
sentiment  {'score': 1.6361, 'answer_confidence': 0.4619, 'abstention': 'abstained', 'low_confidence': True}

With a threshold set, every answer gains abstention (one of passed, abstained, unevaluated) and abstention_threshold. low_confidence: True appears only on the answers that fell below.

The presence of the field is the signal

With min_confidence unset, nothing is written — no abstention, no low_confidence. So the existence of the key tells you a gate ran; its value tells you what happened. unevaluated means a gate ran but the answer carried no usable confidence, which is worth alerting on separately from abstained.

One threshold does not transfer between questions with different option counts. Pass a map keyed by bucket instead, and fit it rather than guessing:

from laya import fit_abstention_thresholds

thresholds = fit_abstention_thresholds(records, temperature, temperature_by_options,
                                       target_error=0.10)
# {'choice:2': 0.91, 'choice:3-5': 0.88, 'score:6-10': 0.79, ...}
router.predict(state, questions, min_confidence=thresholds)

Batch, long docs, many labels

Many states: predict_batch

One route, shared forward passes, answers back in input order. Each request dict may carry its own model, lang, max_len, and head_max_len.

out = router.predict_batch([
    {"state": "I was charged twice.", "questions": q},
    {"state": "The app crashes.",     "questions": q, "max_len": 1024},
], batch_size=8, sort_by_length=True)

# [('english', 'billing',   0.9451),
#  ('english', 'technical', 0.7341)]

sort_by_length groups similar-sized states into each pass, since a pass pads everything to its longest member. It needs a batch_size smaller than the number of requests, or there is no group to reorder.

Long documents

Name the multilingual checkpoint and raise the window. Short inputs give identical answers at max_len=8192, and speed follows real length rather than the limit.

router.predict(long_doc, questions, model="multilingual", max_len=8192)

# or window the document instead of truncating it
router.predict_long(doc, questions)
# noul   -> max P(true) across windows
# choice -> the single most-confident window's answer
# the answer carries answer["window"] = {index, token_start, token_end, count}

Two traps. Name model="multilingual" explicitly for long mostly-English text, or it routes to the 512-token English checkpoint. And predict_long deliberately does not accept max_len or head_max_len — it sizes its own windows from the room each question leaves.

Questions with many labels

A 58-label choice question gives each label a few tokens and gets the accuracy you would expect. Shortlist first, then predict over the survivors:

from laya import predict_shortlist, embed_fn_from_agent

result = predict_shortlist(agent, state, questions,
                           embed_fn=embed_fn_from_agent(agent), k=20)
# result["shortlist"] records what was reranked, per question

Typed output

decide() maps a schema onto questions and hands back schema-shaped values, so nothing downstream parses a label string. A plain JSON-schema dict needs no extra dependency; a pydantic model needs laya[structured].

import laya

schema = {"type": "object", "properties": {
    "department":  {"type": "string",  "enum": ["billing", "technical", "other"]},
    "urgency":     {"type": "integer", "minimum": 0, "maximum": 2},
    "needs_human": {"type": "boolean"}}}

router.decide("I was charged twice, refund me or I cancel.", schema=schema)
# {'department': 'billing', 'urgency': 2, 'needs_human': False}
Schema constructBecomesNotes
enum, constchoiceoriginal values are returned, not the labels
booleannoulan all-bool enum also routes here

Optional[X]unwrapexactly one non-null branch
string, array, nested object—rejected with an error naming the path

With min_confidence=, a field below threshold comes back as None in the values rather than a guess. Ask for return_details=True and you get a DecisionResult carrying the raw distributions, per-field confidences, usage and routing alongside the projected values — so an abstention is still inspectable.

Limits: 32 properties, 32 options, 10 score levels.

laya "I was charged twice"                       # routing only, no download
laya "I was charged twice" --preset triage --predict  # --predict loads the checkpoint
laya "Mein Konto wurde zweimal belastet" --lang de

--questions takes the same dict the SDK takes, as JSON: either the mapping, or {"state_key": "body", "questions": {...}} when the instructions name a field other than the default request. That is the payoff for the backtick convention above.

--lang is decisive — it picks the checkpoint and skips detection. --lang-guess is the soft sibling: it nudges routing but still falls through to the detector. --min-confidence requires one of --predict, --preset or --questions, and errors clearly if you forget.

Mode 1: routing, which loads no weights

$ laya "I was charged twice"
Model     : english
Reason    : English Latin text
Detected  : {"script": "latin", "language": "en", "is_english": true, ...}

This is the default. No checkpoint is touched, so the whole process finishes in about 40 ms — fast enough to shell out to per request, and useful on its own if all you need is which model and language a request resolves to.

Mode 2: answering

Three ways to supply the questions. --predict is what loads the checkpoint.

laya "..." --predict                      # the router questions (difficulty, domain, needs_tools, is_sensitive)
laya "..." --preset triage --predict        # a preset; implies --predict
laya "..." --questions q.json               # your own questions; implies --predict
$ laya "I was charged twice, refund me or I cancel" --preset triage --predict

intent      : refund (p=0.899)
is_urgent   : 0.154
frustration : 1.87
refund_requested: 0.909
churn_risk  : 0.089
Read that last line before trusting the preset

The message says "or I cancel", and the triage preset's churn_risk reads 0.089. An equivalent question worded "Does `message` threaten to cancel or leave?" scores 0.84 on the longer version of the same complaint. The preset asks a subtly different thing — whether the customer may leave — but a near-zero on an explicit cancellation threat is exactly the miss that breaks a churn-escalation rule. Test presets against your own data rather than adopting them on the strength of their names.

Mode 3: batch

laya --batch tickets.txt                              # routing only, one aligned line per request
laya --batch tickets.txt --predict --json             # JSONL, one object per request
cat tickets.txt | laya --batch - --predict --json     # stdin
laya --batch tickets.txt --predict --batch-size 8 --sort-by-length
$ laya --batch tickets.txt
english        English Latin text  <- I was charged twice
multilingual   Latin script but language looks like 'de', not English  <- Guten Tag, ...
english        English Latin text  <- The app crashes on launch

--batch-size bounds how many requests share a forward pass, and --sort-by-length groups similar sizes inside it — a pass pads everything to its longest member, so mixing a two-line request with a two-paragraph one wastes most of the compute. The flag needs a --batch-size below the number of requests, since one pass over the whole file has no group to reorder.

A mixed-language batch loads more than one checkpoint

Routing runs per request, so one German line in an English batch pulled in the 322M multilingual checkpoint on top of the 421M English one. That is correct behaviour and worth knowing before you point a batch at a multilingual pile on a small machine. Force it with --model if you would rather pay for one model.

laya-evals takes a JSONL dataset, not the plain-text lines --batch accepts. Handing it a text file fails with is not valid JSON: Expecting value: line 1 column 1, which is the error to expect if you mix the two up.

Mode 4: interactive

Run laya with no text and you get a REPL sharing one Router across requests, so the checkpoint loads once. quit, exit or Ctrl-D ends it.

$ laya
Laya interactive mode. Type a request and press Enter; Ctrl-D or 'quit' to exit.
laya>

What the CLI cannot do

The command line covers routing, prediction, presets, your own questions, batch and the confidence flag. These are library-only, and no flag reaches them:

  • decide() / decide_batch() — schema-driven typed output, including abstaining a field to None
  • hooks — logging, metrics, and ctx.skip caching
  • calibration — records_from_labeled, temperature and threshold fitting
  • shortlist for high-cardinality choice questions
  • predict_long windowed scanning, and per-request token budgets inside a batch
  • agent-level options such as compile and fast

Batch mode also assumes one request per line. When each request needs its own question set, use predict_batch with a list of request dicts instead.

Hooks

Six lifecycle events: on_route, on_load, on_evict, on_predict_start, on_predict_end, on_error. Subclass BaseHook and implement only what you need.

from laya import BaseHook

class Metrics(BaseHook):
    def on_route(self, ctx):
        print("chose", ctx.decision["model"])

    def on_predict_end(self, ctx):
        print(ctx.model, ctx.elapsed_ms, ctx.usage)

router = Router(hooks=[Metrics()], hooks_raise=False, hooks_timeout=0.05)

ctx carries states, questions, results, decision, model, usage, elapsed_ms, a per-call run_id, and error. Start hooks may rewrite ctx.states, ctx.questions and the token budgets; end hooks may rewrite ctx.results.

A start hook that has a cached answer calls ctx.skip([...]) with one result per state, and inference is skipped while the end hooks still run. That is the caching seam.

hooks_raise=True (the default) lets a broken hook fail the request; set it false to downgrade to a warning. hooks_timeout bounds each hook call on a worker thread — it protects the request, not the process, since the thread cannot be interrupted. Hooks registered per call run after the installed ones.

Accuracy and calibration

Zero-shot works, but how well depends entirely on how close your questions sit to what the model was trained on. Fine-tuning is the lever that fixes the rest, and it is expensive enough to be worth understanding before you reach for it.

What the zero-shot number actually measures

The headline figure is that a fine-tuned checkpoint scores 0.766 against 0.362 for the base english checkpoint on the project's typed-decisions benchmark. That is a real gain, but the comparison is only meaningful with the baseline it sits on:

ModelKindAccuracyECE
Random baseline—0.318—
Base english checkpointzero-shot0.362—
ModernBERT-base (149M)specialist0.6460.179
TypeSafe Jev 1.13.0general0.7270.144
Teacher self-agreementceiling0.735—

The benchmark is 2,000 decisions across four workflows — agent trace observability, customer service, invoice processing and security incidents — with targets taken from a teacher model's probability distributions. The base checkpoint at 0.362 is barely off the random baseline of 0.318.

That is the crucial qualification: 0.362 is the score on arbitrary typed-decision questions, not on laya's own presets. So the size of the fine-tuning win depends on where your questions fall:

  • Questions resembling the shipped presets (triage_questions(), guard_questions()) sit near the model's training distribution. Zero-shot is the right starting point, and fine-tuning may buy little.
  • A bespoke label set — your own categories, your own scale, your own definition of "urgent" — is the regime where zero-shot is close to a coin flip and fine-tuning is what makes the thing work at all.
Confidence is not accuracy

answer_confidence tells you the model's certainty, not its correctness. A question can return 0.98 and still be wrong. Only a labeled held-out set tells you which side of the line above you are on.

Cheaper levers, before you spend GPU hours

1. Check truncation first. On long inputs, a large share of "the model got it wrong" is the state having been silently trimmed. Read usage["truncated"] before tuning anything.

2. Fix the question, not the model. The tour measures one noul question twice, with and without custom labels, and gets 0.37 and 0.54. The wording the model reads is part of the question. No amount of training resolves an ambiguous instruction — you would only be training the model to imitate your own ambiguity.

3. Fit temperatures on labeled data. This changes confidence only: temperature scaling leaves argmax and accuracy untouched. It is what makes gating meaningful.

from laya import fit_temperatures, records_from_labeled

records = records_from_labeled(agent, labeled_pairs)
temperature = fit_temperatures(records)

agent.save_calibration("calibration.json")   # temperatures + checkpoint identity, no weights
agent.load_calibration("calibration.json")

4. Fit abstention thresholds. Also not an accuracy change, but it converts "accuracy" into "accuracy on what it chose to answer", which is usually the number that matters operationally. The default targets a 10% error rate per option-count bucket:

from laya import fit_abstention_thresholds

thresholds = fit_abstention_thresholds(records, temperature, temperature_by_options,
                                       target_error=0.10)
router.predict(state, questions, min_confidence=thresholds)

5. If a bucket stays miscalibrated, bin it. Temperature scaling applies one scalar per bucket, so it cannot repair a bucket whose reliability curve is not a simple sharpening or softening. The shipped choice:11+ entry is exactly that case, and it is why the warning below appears at all. Histogram binning is the non-parametric alternative, and it composes on top of the temperature map rather than replacing it:

from laya import fit_binning_map, apply_binning_map

binning = fit_binning_map(records, temperature, temperature_by_options, bins=15)
# {bucket: {"bins": 15, "values": [...]}} -- buckets below the floor (200) are omitted,
# and an empty bin maps to its own midpoint so an unseen value is never forced to 0

confidence = apply_binning_map(answer_confidence, bucket, binning)

Calibration is not the same lever as training

It is worth being precise about what each one changes. Calibration alters what the numbers mean — it re-scales confidence so a threshold means what you think it means. Fine-tuning alters what the model answers. The first is cheap, needs a few hundred labeled examples, and never changes an argmax. The second needs a teacher, a GPU and a training loop.

So: run the cheap levers, measure on held-out data, and only then decide whether the accuracy gap justifies training. The full workflow — data, objective, recipe, cost and failure modes — has its own section: Fine-tuning.

The clamp that produces that warning

On first load the shipped english checkpoint emits this:

RuntimeWarning: laya: this checkpoint ships invalid temperatures or values
outside [0.5, 5]; using choice:11+=0.1005 -> 0.5. Treat confidence from the
affected entries as uncalibrated.

Only the choice:11+ bucket is affected — choice questions with eleven or more options. A three-option question like department is untouched, and argmax answers are unaffected either way.

The cause is a mismatch worth knowing about, because it will bite you the moment you fit your own temperatures: the fitters accept values in [0.1, 10], but the agent clamps to [0.5, 5.0] on load. The shipped 0.1006 therefore runs as 0.5. Edit agent.temperature_by_options — the copy predict() actually reads — rather than agent.cfg, or a value below 0.5 will silently run clamped.

Fine-tuning

Zero-shot sits barely above chance on a bespoke label set, and fine-tuning is what fixes that. This is the whole workflow: what data you need, what the objective rewards, the recipe, the cost, and the ways it fails.

What you need before you start

  • Labeled examples that fit the three primitives. A choice, a scale, or a yes/no — reshape anything else first.
  • A teacher whose probabilities you trust. Targets are distributions, not labels, so the teacher's quality is the ceiling on yours.
  • A GPU budget. A free Kaggle 2×T4 session covers the demo set; a 30k-question set is a few hours.
  • Willingness to write the loop. The pip package ships no trainer.

The data

A training item is one (state, question) pair carrying a target distribution over that question's options. Not a hard label. This is the single most important thing to get right, because the entire calibration story depends on it.

Where targets come from, in practice:

  • A stronger model's distribution. Put the question to a frontier LLM and take its probability over each option. This is what the project's own demo set does.
  • Multi-labeler agreement. If several people label the same item, their agreement rate gives you a soft target — five of six agreeing becomes 0.83. More work, but it captures genuine human ambiguity rather than one model's idiosyncrasy.
You are teaching the model your noise

RLCD imitates whatever distribution you hand it. If the teacher is inconsistent about a class, the fine-tuned model learns that inconsistency faithfully. Measure teacher agreement on a sample before spending hours on the full set.

The demo set is 1,200 cases expanding to 6,000 typed decisions across four workflows. Tokenized items are cached to a PyTorch pickle (train_items.pt) with a .meta.json sidecar, keyed by model directory, token budgets, dataset and split — so changing any of those invalidates the cache automatically. Items whose marker count does not match the option count are dropped.

One tokenized item is {ids, markers, qtype, target, label}: token ids, option positions, question type, target distribution, and its argmax. The demo dataset stores rows as string-encoded JSON fields (id, workflow, state, questions, gold). To use your own data, keep that row schema and replace the two loader calls.

No minimum dataset size is documented anywhere, and there is no guidance on overfitting — the demo simply uses 1,200 cases. Treat that as a starting point rather than a recommendation, and track held-out accuracy as you scale.

The objective is a proper scoring rule

The method is RLCD, and the design choice that matters is that the reward is a strictly proper scoring rule. Proper means it is maximised by reporting your true belief, which is exactly why the output probabilities stay meaningful instead of collapsing into overconfident point estimates. A cross-entropy-only objective would train the model to be decisive rather than calibrated. From the installed source:

# laya.common.proper_reward -- strictly proper scoring rule
log_score = (target · log q)                      # floored at -9.21 nats
sph       = (target · q) / ‖q‖                 # spherical score
reward    = log_score + w_sph · sph

# the ranked probability term applies to score-type questions only
reward   -= w_rps · RPS · is_score
The weights differ between the library and the scripts

The library default is w_sph=0.5. The fine-tuning scripts pass 0.75. If you call proper_reward yourself, you are not matching their recipe unless you pass it explicitly.

Each step draws 4 noisy samples of the clean logits, with Gaussian noise whose scale σ is annealed from 0.4 down to 0.1 across epochs. Reward is computed under no_grad, the advantage is normalised against the group (the GRPO baseline), and the policy term is a Gaussian log-density on the noisy versus clean logits. A cross-entropy term is added alongside. There is also an activation term in the loss, but it is multiplied by 0.0, so it contributes nothing.

td_lambda_targets exists in the library for multi-turn conversation trajectories, and is not used by either fine-tuning script — the typed-decisions data is single-turn.

The loop

Six steps, in this order. Calibration happens inside the training run, not as an afterthought.

1. preprocess — tokenize every training case to soft targets, write the pickle both ranks read
2. train — 4 epochs, DDP across the GPUs
3. calibrate — fit one temperature per question type, on rank 0, after the last epoch
4. evaluate — predict the held-out split, record metrics and per-case latency
5. export — write the checkpoint directory
6. publish — optional: model card plus benchmark report to the Hub

On the Kaggle 2×T4 path the training step is a DDP launch:

torchrun --standalone --nproc_per_node=2 train_ddp.py

For a single machine there is a standalone script that runs the same loop on MPS or CPU:

python notebooks/laya_finetune_typed_decisions_mps.py --epochs 2 --micro-batch 1 --grad-accum 32
python notebooks/laya_finetune_typed_decisions_mps.py --device cpu
python notebooks/laya_finetune_typed_decisions_mps.py --model-dir ./laya_base --items ./train_items.pt

Calibration runs inside the loop

After the final epoch, one temperature per question type is fit by LBFGS on the log-temperature, minimising the negative log-likelihood of the temperature-scaled logits. Two details matter more than the optimisation itself:

  • The holdout is taken before sharding. --calib-max (400) items are drawn from the front of a seeded shuffle before the data is split across DDP ranks, so every rank fits on the same slice. It is about 10% of the demo set — enough to fit three scalars, not enough to validate against. Hold out your own eval data separately.
  • Inherited temperature_by_options must be removed. The bucket map takes precedence over the per-type scalar at inference, so a checkpoint that carries an inherited map will silently mask your new fit. The notebook deletes it when writing rl_agent_config.json. Ship the config, not just the weights.

If fewer than ten samples land in a group the fit returns 1.0, and an empty group defaults to 1.2. Remember that the agent clamps everything to [0.5, 5.0] on load, no matter what the fitter produced — the same clamp that produces the warning described in Accuracy and calibration.

Evaluating the result

The notebook computes a wider set than accuracy alone: accuracy, soft accuracy, Brier score, ECE, score MAE, within-one-level, KL divergence, total variation, latency p50 and p95, cost per case, and a per-workflow accuracy breakdown. The per-workflow column is the one to read first — an aggregate can improve while one workflow regresses.

No release gates ship with this

There is no accuracy, ECE or AURC threshold in the fine-tuning code that blocks a bad model from being published. The project reports its numbers against the baselines in the previous section and stops there. You define the acceptance bar, which means you also have to hold out the data to measure against it.

What you get

The export is an ordinary laya checkpoint directory, which means it loads through the same API as anything else:

your-checkpoint/
  model.safetensors        # full state dict, half precision
  encoder/                 # config + weights
  tokenizer/
  rl_agent_config.json     # per-type temperatures, fine_tuned flag
  checkpoint_meta.json
import laya

agent = laya.load("your-org/your-checkpoint")
agent.predict(state, questions)   # same call, same answer shape as any other checkpoint

A rolling checkpoint_latest/ is overwritten each epoch, so a timeout or an OOM costs you one epoch rather than the run. On publish the directory also gains a model card and benchmark_report.json.

How fine-tuning fails

The project's browser-agent case study is the most useful evidence available, precisely because the run did not go cleanly. The failure modes it documents are the ones to watch for in your own data:

  • Class-imbalance leaks teach shortcuts. When every positive example happened to include a prior action and no negative example did, the model learned "any history → DONE" — a spurious correlation, not the task. Mid-task negatives are needed to break it.
  • Templated phrasing leaks. Positives generated from a template share wording, and the model learns the template instead of the concept. Positives must be real, varied examples.
  • A narrow dataset starves rare classes. One source contained no examples of an entire operation, so that class was effectively untrainable until it was re-weighted.
  • Truncation can cost accuracy silently. Cutting page text to 3,000 characters saved no time — the option head dominates the sequence — and cost 0.04 top-1 accuracy.
  • Run-to-run variance can exceed real differences. In that study the variance between seeds was larger than the gap between two different backbone sizes, which means a single run cannot tell you which model is better.
  • Escalating to a bigger model can make things worse. Confidence-gated routing to a local 8B/27B model performed worse than the 421M head it was meant to improve on.
A fine-tuned model is not automatically better

Every one of those failures produced a model that trained successfully and scored worse. Budget for an evaluation harness and a baseline, not just a training run.

Gotchas

  • Router(models=...) is pluralmodel= is a per-call argument on predict. Passing model= to the constructor is silently a different thing to reach for.
  • noul returns P(true), alwaysDescriptive criteria and labels change the text the model sees. The number is still P(true), so a confident "no" is a low number with high answer_confidence.
  • Gate on answer_confidence, not confidenceEntropy confidence drifts with option count, so a threshold on it does not transfer between questions.
  • A list state is a conversationA list is JSON-serialized as ordered turns, newest last, and truncates from the left so the newest turn survives. Strings and dicts truncate from the right.
  • Empty questions skip inferencequestions={} returns empty answers with zero tokens and no forward pass. Useful as a short-circuit; a surprise if you expected an error.
  • predict_long takes no token budgetsIt sizes its own windows. Pass max_len on predict instead, or use max_len=8192 with model="multilingual".
  • Agent options go through agent_kwargsfast, compile and lang_temperatures are Agent arguments. On a Router they reach it via agent_kwargs={...}.
  • Adding questions is nearly free; splitting calls is notEight questions in one predict is one forward pass. Eight predict calls is eight.
  • max_loaded is 2 by defaultAn LRU over checkpoints. preload=True loads all three and raises the cap; it is not an out-of-memory remedy.

The example tour

main.py in the repository is a twelve-section tour that runs end to end against the cached english checkpoint — no extra downloads, no configuration. Every number it prints is real output, which is why three of its sections report a result the model got wrong rather than a tidy one.

Read the whole file at github.com/machinelearning2014/laya-how-to/blob/main/main.py, or run it with .venv/bin/python main.py. The core pattern it is built around:

the core pattern, from main.py 
from laya import Router

router = Router()  # downloads a checkpoint on first use

state = "Hi, we were billed twice for March. Please refund the duplicate today or we will cancel our plan."
questions = {
    "department": {"type": "choice", "instructions": "Which department should handle `message`?",
                   "criteria": {"billing": "invoices, payments, refunds",
                                "technical": "bugs, outages, system errors",
                                "other": "everything else"}},
    "urgency": {"type": "score", "instructions": "How urgent is `message`?",
                "criteria": ["not urgent", "soon", "blocking"]},
    "churn_risk": {"type": "noul", "instructions": "Does `message` threaten to cancel or leave?"},
    # ... four more, including a noul carrying custom labels
}

result = router.predict(state, questions)

result["answers"]["department"]["choice"]             # billing
result["answers"]["department"]["answer_confidence"]  # 0.9875 -- max(p)
result["answers"]["urgency"]["score"]                # 1.7901 -- 0..2 scale
result["answers"]["churn_risk"]["noul"]              # 0.8429 -- P(true)
result["routing"]["model"]                           # english

What the tour covers

02 questions — all three types, criteria dicts, and what custom labels actually change

05 abstention — min_confidence, per-bucket maps, the temperature clamp

07 presets — all five, the backtick convention, the email and language helpers

Each area is a function, called in order by main() behind an if __name__ == "__main__" guard — so import main hands you the question set without running inference.

Three sections report a wrong answer, on purpose

The tour runs against a real model, so it shows three rough edges rather than tidying them away. A schema-derived score question carries level texts "0", "1", "2" and no descriptions, so decide() reads urgency: 0 on a message that demands a refund today. Relabelling a noul with custom labels moved its P(true) from 0.37 to 0.54 — labels change what the model reads, not only what you see. And shortlisting a twelve-label question down to four dropped both billing and refunds, answering security where the full label set answered refunds.
