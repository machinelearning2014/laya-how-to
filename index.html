Typed decisions in one forward pass

The mental model

You give Laya a state (a string, a dict, or a list of conversation turns) and a dict of typed questions. It routes to a checkpoint and answers every question at once.

The reason it is fast is structural, not an optimization: the state and every question's options are packed into one sequence, with each option occupying its own masked slot. A single forward pass scores all the slots, so eight questions cost about the same as one. That is why predict has no batch dimension to exploit for a single state, and why adding questions is nearly free.

Why this matters for your latency

Adding questions to a request is close to free. Splitting one request into eight separate predict calls is not — that is eight routes and eight forward passes.

Setup and checkpoints

pip install laya                      # Python 3.10+
pip install "laya[structured]"        # adds pydantic, for schema= typed output
pip install "laya[serve]"             # adds the HTTP server
from laya import Router

router = Router()                 # lazy: nothing downloads until the first predict
router = Router(preload=True)        # load all three up front
router = Router(max_loaded=1)         # keep only one checkpoint resident
router = Router(device="cpu")         # pin the device (default: cuda, else mps, else xpu, else cpu)
router = Router(agent_kwargs={"compile": True})   # Agent-level options reach the Router here

Three checkpoints, and the router picks between them per request by detected script and language. Routing itself loads nothing, so it is safe to call on every request.

route() returns the decision without touching a checkpoint — useful as a cheap pre-flight, and as a debugging tool when text is landing on the wrong checkpoint.

# {'model': 'multilingual',

#  'workflow': None}

Route precedence runs: explicit model, then task, then detected workflow, then explicit lang, then lang_guess, then detection, then default.

Constructor is plural

Router(models=...) overrides the checkpoint table. The singular model= is a per-call argument on predict, not a constructor kwarg.

Writing questions

Three types. Each question is a dict with type, instructions, and criteria.

choice

Pick one label. Criteria may be a dict of label to description, or a plain list of labels.

"department": {"type": "choice",
               "instructions": "Which department should handle `message`?",
               "criteria": {"billing": "invoices, payments, refunds",
                            "technical": "bugs, outages, system errors",
                            "other": "everything else"}},

# short form: labels only. None or "" means "no description".
"topic": {"type": "choice", "criteria": ["billing", "technical", "other"]}

score

An ordered scale of any length. You get back the expected level as a float, plus the full distribution.

"urgency": {"type": "score",
            "instructions": "How urgent is `message`?",
            "criteria": ["not urgent", "soon", "blocking"]}   # -> 1.79

noul

A yes/no question under uncertainty. Always returns P(true) in 0..1, whatever you call the two sides.

"churn_risk": {"type": "noul",
               "instructions": "Does `message` threaten to cancel or leave?"}   # -> 0.84

# criteria is optional. If given, it must be keyed exactly true/false.
"refund_requested": {"type": "noul",
                     "instructions": "Does `message` ask for money back?",
                     "criteria": {"true": "asks for a refund or a charge reversed",
                                  "false": "no refund requested"}}

# labels only change the text shown to the model. The number is still P(true).
"labels": {"true": "A", "false": "B"}

The backtick convention

Every preset in the library names the state field it reads inside backticks: "What does the customer want in `message`?". presets.state_field() scrapes that name back out, and the CLI and MCP server use it to know where to put your text. Plain predict with a string state does not need it, but adopting it keeps a question set portable to the CLI and to decide.

Limits worth knowing

  • Each option's rendered text is truncated to 48 tokens. More labels means fewer tokens each.
  • The option head shares head_max_len (default 192). Raise it for many-label questions.
  • Core imposes no cap on question or option counts. The HTTP server does: 64 questions, 100 choice options, 32 score levels, 512 total options.
  • If the masked slots cannot fit inside max_len, you get a ValueError naming the question — and raising head_max_len can make it worse by leaving less room for state.

Reading the result

Four top-level keys: model, answers, usage, routing. The routing key is added by Router; a bare Agent returns the other three.

# choice
{"type": "choice", "choice": "billing",
 "probabilities": {"billing": 0.9875, "technical": 0.0071, "other": 0.0054},
 "confidence": 0.93, "answer_confidence": 0.9875}

# score
{"type": "score", "score": 1.7901,
 "legend": {"0": "not urgent", "1": "soon", "2": "blocking"},
 "probabilities": {"0": 0.0337, "1": 0.1424, "2": 0.8238},
 "confidence": 0.34, "answer_confidence": 0.8238}

# noul
{"type": "noul", "noul": 0.8429,
 "confidence": 0.8429, "answer_confidence": 0.8429}

Every answer also carries "action": {"act_probability": ...} from a separate head. It is always 1.0 in these runs; the examples above omit it for length.

Did the model actually see my whole state?

result["usage"]
# {"input_tokens": 401, "output_tokens": 0, "state_tokens": 21,
#  "state_tokens_dropped": 0, "truncated": False, "truncated_questions": []}

Read usage["truncated"] instead of estimating from string length. Long states are silently trimmed to fit max_len (512 on english, 1024 on multilingual). usage also gains an options entry when the head budget collapsed two options onto the same tokens — a signal that your answer is limited by the budget rather than by the model.

output_tokens is always 0. Laya never generates text.

Confidence and abstention

Two different confidences

Each answer carries both, and they measure different things.

Typeconfidenceanswer_confidence
choicenormalized Shannon entropymax(p), the top option's probability
scorenormalized Shannon entropymax(p), the top level's probability
noulmax(p)max(p) — identical to the above here

Gate on answer_confidence. It is the calibrated quantity — the one temperature scaling fits and ECE measures — and it means the same thing across all three types. The entropy confidence is useful for ranking, but it drifts with how many options a question has, so a threshold on it does not transfer between questions.

Why that distinction bites

Look at the two noul answers from the worked example:

deadline_mentioned returns noul = 0.24, which looks low, but that is a confident no: answer_confidence is 0.76. Gating on the raw noul value would abstain on the model's most decisive answer. sentiment at 0.46 is the one actually worth escalating — it sits between "annoyed" and "angry" and the model is telling you so.

Opt-in abstention

result = router.predict(state, questions, min_confidence=0.9)
department {'choice': 'billing', 'answer_confidence': 0.9875, 'abstention': 'passed'}
sentiment  {'score': 1.6361, 'answer_confidence': 0.4619, 'abstention': 'abstained', 'low_confidence': True}

With a threshold set, every answer gains abstention (one of passed, abstained, unevaluated) and abstention_threshold. low_confidence: True appears only on the answers that fell below.

The presence of the field is the signal

With min_confidence unset, nothing is written — no abstention, no low_confidence. So the existence of the key tells you a gate ran; its value tells you what happened. unevaluated means a gate ran but the answer carried no usable confidence, which is worth alerting on separately from abstained.

One threshold does not transfer between questions with different option counts. Pass a map keyed by bucket instead, and fit it rather than guessing:

from laya import fit_abstention_thresholds

thresholds = fit_abstention_thresholds(records, temperature, temperature_by_options,
                                       target_error=0.10)
# {'choice:2': 0.91, 'choice:3-5': 0.88, 'score:6-10': 0.79, ...}
router.predict(state, questions, min_confidence=thresholds)

Batch, long docs, many labels

Many states: predict_batch

One route, shared forward passes, answers back in input order. Each request dict may carry its own model, lang, max_len, and head_max_len.

out = router.predict_batch([
    {"state": "I was charged twice.", "questions": q},
    {"state": "The app crashes.",     "questions": q, "max_len": 1024},
], batch_size=8, sort_by_length=True)

# [('english', 'billing',   0.9451),
#  ('english', 'technical', 0.7341)]

sort_by_length groups similar-sized states into each pass, since a pass pads everything to its longest member. It needs a batch_size smaller than the number of requests, or there is no group to reorder.

Long documents

Name the multilingual checkpoint and raise the window. Short inputs give identical answers at max_len=8192, and speed follows real length rather than the limit.

router.predict(long_doc, questions, model="multilingual", max_len=8192)

# or window the document instead of truncating it
router.predict_long(doc, questions)
# noul   -> max P(true) across windows
# choice -> the single most-confident window's answer
# the answer carries answer["window"] = {index, token_start, token_end, count}

Two traps. Name model="multilingual" explicitly for long mostly-English text, or it routes to the 512-token English checkpoint. And predict_long deliberately does not accept max_len or head_max_len — it sizes its own windows from the room each question leaves.

Questions with many labels

A 58-label choice question gives each label a few tokens and gets the accuracy you would expect. Shortlist first, then predict over the survivors:

from laya import predict_shortlist, embed_fn_from_agent

result = predict_shortlist(agent, state, questions,
                           embed_fn=embed_fn_from_agent(agent), k=20)
# result["shortlist"] records what was reranked, per question

Typed output

decide() maps a schema onto questions and hands back schema-shaped values, so nothing downstream parses a label string. A plain JSON-schema dict needs no extra dependency; a pydantic model needs laya[structured].

import laya

schema = {"type": "object", "properties": {
    "department":  {"type": "string",  "enum": ["billing", "technical", "other"]},
    "urgency":     {"type": "integer", "minimum": 0, "maximum": 2},
    "needs_human": {"type": "boolean"}}}

router.decide("I was charged twice, refund me or I cancel.", schema=schema)
# {'department': 'billing', 'urgency': 2, 'needs_human': False}
Schema constructBecomesNotes
enum, constchoiceoriginal values are returned, not the labels
booleannoulan all-bool enum also routes here

string, array, nested object—rejected with an error naming the path

With min_confidence=, a field below threshold comes back as None in the values rather than a guess. Ask for return_details=True and you get a DecisionResult carrying the raw distributions, per-field confidences, usage and routing alongside the projected values — so an abstention is still inspectable.

Limits: 32 properties, 32 options, 10 score levels.

laya "I was charged twice"                       # routing only, no download
laya "I was charged twice" --preset triage --predict  # --predict loads the checkpoint
laya "Mein Konto wurde zweimal belastet" --lang de
laya "My payment failed" --lang-guess en               # soft hint, still falls through to detection
laya "Refactor this service" --model ml --predict
laya --batch tickets.txt --predict --json              # JSONL; - means stdin
laya --batch tickets.txt --predict --batch-size 8 --sort-by-length
laya "Where is my card" --questions intents.json        # implies --predict
laya "Refund my card" --predict --min-confidence 0.9
laya                                                   # interactive REPL

--questions takes the same dict the SDK takes, as JSON: either the mapping, or {"state_key": "body", "questions": {...}} when the instructions name a field other than the default request. That is the payoff for the backtick convention above.

--lang is decisive — it picks the checkpoint and skips detection. --lang-guess is the soft sibling: it nudges routing but still falls through to the detector. --min-confidence requires one of --predict, --preset or --questions, and errors clearly if you forget.

Serving and integrations

HTTP

pip install "laya[serve]"
laya-serve                       # POST /v1/systemone, /v1/systemone/batch, GET /health

Deployment knobs are environment variables: LAYA_API_KEY (adds bearer auth), LAYA_MAX_LOADED, LAYA_DEFAULT_MODEL, LAYA_MAX_CONCURRENT (excess gets a 503 with Retry-After), LAYA_MAX_TOKEN_BUDGET (caps per-request token budgets), LAYA_REVISION (pin a commit, or the literal reviewed), and LAYA_JEV_STRICT to project responses onto a strict wire contract for clients that reject unknown fields. With LAYA_API_KEY set, /health keeps answering liveness but requires the bearer for checkpoint and device detail.

pip install "laya[mcp]"

Evaluation

Hooks

Six lifecycle events: on_route, on_load, on_evict, on_predict_start, on_predict_end, on_error. Subclass BaseHook and implement only what you need.

from laya import BaseHook

class Metrics(BaseHook):
    def on_route(self, ctx):
        print("chose", ctx.decision["model"])

    def on_predict_end(self, ctx):
        print(ctx.model, ctx.elapsed_ms, ctx.usage)

router = Router(hooks=[Metrics()], hooks_raise=False, hooks_timeout=0.05)

ctx carries states, questions, results, decision, model, usage, elapsed_ms, a per-call run_id, and error. Start hooks may rewrite ctx.states, ctx.questions and the token budgets; end hooks may rewrite ctx.results.

A start hook that has a cached answer calls ctx.skip([...]) with one result per state, and inference is skipped while the end hooks still run. That is the caching seam.

hooks_raise=True (the default) lets a broken hook fail the request; set it false to downgrade to a warning. hooks_timeout bounds each hook call on a worker thread — it protects the request, not the process, since the thread cannot be interrupted. Hooks registered per call run after the installed ones.

Accuracy and calibration

The shipped checkpoints work zero-shot. Fine-tuning on decisions from your own domain is where accuracy jumps: on the project's own typed-decisions benchmark, a fine-tuned checkpoint scored 0.766 against 0.362 for the base checkpoint on the same decisions. Treat zero-shot as a good default and a fine-tuned model as the real product.

Before fine-tuning, two cheaper levers. Fit temperatures on labeled data, then fit abstention thresholds on the calibrated output:

from laya import fit_temperatures, records_from_labeled

records = records_from_labeled(agent, labeled_pairs)
temperature = fit_temperatures(records)

agent.save_calibration("calibration.json")   # temperatures + checkpoint identity, no weights
agent.load_calibration("calibration.json")

The warning you will probably see

On first load the shipped english checkpoint emits this:

RuntimeWarning: laya: this checkpoint ships invalid temperatures or values
outside [0.5, 5]; using choice:11+=0.1005 -> 0.5. Treat confidence from the
affected entries as uncalibrated.

Only the choice:11+ bucket is affected — choice questions with eleven or more options. A three-option question like department is untouched, and argmax answers are unaffected either way. If you have wide choice questions, gate on answer_confidence only after fitting temperatures, or check the reliability curve first.

Check truncation before blaming the model

Most "the model got it wrong" reports on long inputs are usage["truncated"] == True. Verify that before tuning anything.

Gotchas

  • Router(models=...) is pluralmodel= is a per-call argument on predict. Passing model= to the constructor is silently a different thing to reach for.
  • noul returns P(true), alwaysDescriptive criteria and labels change the text the model sees. The number is still P(true), so a confident "no" is a low number with high answer_confidence.
  • Gate on answer_confidence, not confidenceEntropy confidence drifts with option count, so a threshold on it does not transfer between questions.
  • A list state is a conversationA list is JSON-serialized as ordered turns, newest last, and truncates from the left so the newest turn survives. Strings and dicts truncate from the right.
  • Empty questions skip inferencequestions={} returns empty answers with zero tokens and no forward pass. Useful as a short-circuit; a surprise if you expected an error.
  • predict_long takes no token budgetsIt sizes its own windows. Pass max_len on predict instead, or use max_len=8192 with model="multilingual".
  • Agent options go through agent_kwargsfast, compile and lang_temperatures are Agent arguments. On a Router they reach it via agent_kwargs={...}.
  • Adding questions is nearly free; splitting calls is notEight questions in one predict is one forward pass. Eight predict calls is eight.
  • max_loaded is 2 by defaultAn LRU over checkpoints. preload=True loads all three and raises the cap; it is not an out-of-memory remedy.

The worked example

Eight questions over one support message: two scores, four nouls, one choice. Every number below is real output from this file.

main.py 
from laya import Router

router = Router()  # downloads a checkpoint on first use

state = "Hi, we were billed twice for March. Please refund the duplicate today or we will cancel our plan."
questions = {
    "department": {"type": "choice", "instructions": "Which department should handle `message`?",
                   "criteria": {"billing": "invoices, payments, refunds",
                                "technical": "bugs, outages, system errors",
                                "other": "everything else"}},
    "urgency": {"type": "score", "instructions": "How urgent is `message`?",
                "criteria": ["not urgent", "soon", "blocking"]},
    "churn_risk": {"type": "noul", "instructions": "Does `message` threaten to cancel or leave?"},
    "sentiment": {"type": "score", "instructions": "How unhappy is the user in `message`?",
                  "criteria": ["neutral", "annoyed", "angry", "furious"]},
    "refund_requested": {"type": "noul", "instructions": "Does `message` ask for money back?",
                         "criteria": {"true": "asks for a refund or a charge reversed",
                                      "false": "no refund requested"}},
    "deadline_mentioned": {"type": "noul",
                           "instructions": "Does `message` name a deadline or time pressure?"},
    "security_related": {"type": "noul",
                         "instructions": "Does `message` report fraud, account compromise or a data breach?"},
}

def main() -> None:
    result = router.predict(state, questions)

    print(result["answers"]["department"]["choice"])            # billing
    print(result["answers"]["department"]["answer_confidence"])  # 0.9875 -- max(p)
    print(result["answers"]["urgency"]["score"])                # 1.79  -- 0..2 scale
    print(result["answers"]["churn_risk"]["noul"])              # 0.84  -- P(true)
    print(result["answers"]["sentiment"]["score"])              # 1.64  -- 0..3 scale
    print(result["answers"]["refund_requested"]["noul"])        # 0.91
    print(result["answers"]["deadline_mentioned"]["noul"])      # 0.24  -- a confident no
    print(result["answers"]["security_related"]["noul"])        # 0.37
    print(result["routing"]["model"])                           # english


if __name__ == "__main__":
    main()

What this example demonstrates

choice — a dict of criteria with descriptions, read via ["choice"]
score — two different scale lengths, read as an expected level via ["score"]
noul — both bare and with true/false criteria, read as P(true) via ["noul"]
routing — reading which checkpoint answered
convention — backticked `message` in every instruction, so presets.state_field() resolves and the set is portable to the CLI

The __main__ guard keeps import main from running inference, which matters as soon as you want to reuse the question set from a test or a notebook.

Two questions disagree, and that is information

urgency reads 1.79 ("blocking") while deadline_mentioned reads a confident no. Both can be true: the message is urgent in tone but names no actual deadline. If your routing depends on genuine time pressure, ask about the deadline and ignore the urgency score — or tighten the urgency criteria so "urgent tone" and "hard deadline" are not conflated in one scale.
